# Reviewer 2 — empirical software engineering — round 1

This is an **automated review**, not an independent human peer review. I inspected the manuscript, benchmark generator/datasheet, experimental runner and processor/protocol, baselines, processed summary/statistical/public-replay results, and actual E01/E05/E06/E09/E10/E11 raw records from `campaign-20261106T204751600444Z`. I also executed small generator comparisons. I did not rerun the entire campaign.

## Summary

HEARTNESS integrates immutable artifact histories, provenance queries, lifecycle guards, finite checking and observation-based monitoring. Its synthetic query results are consistent with the supplied construction oracle; complete capture ties capture-only provenance exactly. The paper deserves credit for explicitly disclosing weak recovery baselines, synthetic evidence, failed initial correspondence, finite scope, hidden-action misses and substantial monitor cost. The statistics use paired seeds and seed clustering rather than treating graph nodes as replicates. However, several advertised experimental dimensions are ineffective or absent, and the experiments do not yet isolate the benefit of most lifecycle components. The artifact supports a useful controlled feasibility demonstration, but currently provides insufficient empirical depth for a strong TSE evaluation.

## Major concerns and required actions

1. **The benchmark does not exercise independent dependency effects or distinct incident families.** In `benchmark/generate.py`, dependencies are selected only from sources. Thus dependency reachability adds no new full-capture impact targets, although the approach makes an important distinction between historical derivation and present compatibility. With the default seed, `faulty_lesson`, `regression`, `external_effect`, `benign` and `adversarial` generate identical artifacts and active sets; only truth metadata differs. No generated graph has an actual injected stale capability, cyclic attempt or validated/load drift. The manuscript acknowledges shared construction, but 810 labeled cases still provide much less diversity than the nine names suggest. **Required action:** add construction-labeled dependency-only consumers and mixed derivation/use chains, including inactive ancestors and deployment-only affected consumers; exercise actual family-specific event challenges where family-level fault claims are made. Report case counts and outcomes separately for graph queries versus enacted lifecycle incidents. If a family remains only metadata, remove it from the evidence count for incident detection. Preserve existing campaigns as historical rather than silently replacing raw files.

2. **A structural robustness factor is ineffective, and deployment perturbation does not affect the evaluated outputs.** Source count is bounded by `2 if ... else 1`, so `fanout=3` and `fanout=6` produce identical scenarios at the same seed; I verified this directly. E10 changes deployment count, but `trace_record` passes only `scenario['active']` to `query`; deployment membership never enters the scored impact truth or query. Also, `process.py` writes E10 rows to the generic CSV but its `summary['robustness']` contains graph-scale and family-exclusion results rather than an E10 factor analysis. **Required action:** either implement and test meaningful fan-out values and deployment-sensitive metrics, or rename/remove the ineffective factors and revise the protocol claims. Add a processed factor table with actual realized source counts, depth and membership variation, query accuracy and relevant costs; document intentional duplicates rather than treating them as additional robustness evidence.

3. **The ablation experiment does not measure most ablated mechanisms.** E04 replays one withdrawal fixture; disabling P1/P3/P4/P5/P6/P7/P9/P10 and contracts yields identical outputs. More seriously, `latent_mutant_found` invokes the same separate `bfs(2, 9, 'P4')` for every enabled setting, and `observed_drift_detected` mostly switches a Boolean around the same independent monitor call. These results are not evidence of the effect of removing the corresponding component from an evaluated system. The paper admits fixture coverage limits, but the required per-property/component ablation is still unfulfilled. **Required action:** build a targeted challenge matrix with at least one activating operation sequence per supported guard/component and a negative control. Compute measured findings from the configured system, not a predetermined switch. Report redundancy honestly when another guard still prevents the fault. Distinguish prevention, post-state detection, prospective search and observation detection; these are different endpoints.

4. **B3 has no empirical comparison, and the existing baseline comparison chiefly tests access to information.** `linter` is defined and unit tested, but never imported/called by `experiments/run.py`; no B3 result exists in the selected campaign or processed statistics. Statements about what the linter misses are therefore analytical examples rather than measured baseline results. B0 ignores copy detection and B1 uses one fixed token threshold; the paper appropriately avoids stronger competitive claims. **Required action:** run B3 on the same injected current-state violations/benign controls, and report detection/false alarms with its scope explicit. For this feasibility paper, retaining B0/B1 as clearly labeled weak information controls is acceptable; do not present their significance as evidence of a superior recovery algorithm. If competitive recovery claims are retained in later versions, add real Git copy/history and a development-set-tuned text recovery baseline.

5. **Oracle validation lacks a test independent of the evaluated query implementation.** The carried integer labels are algorithmically separate from graph traversal, which is useful. However, the twelve-case `benchmark_audit.json` is constructed by comparing `outputs['ours']['queries']` with generator truth. That is an additional correctness check on the same evaluated method, not independent benchmark validation. Common schema/authorship is acknowledged but cannot be repaired by more seeds. **Required action:** add independently specified hand-worked cases covering source-only, dependency-only, mixed paths, disconnected/deployment-only membership, inactive revisions and empty truth. Record the expected sets before invoking the tool, and explicitly separate schema/generator sanity checks from agreement with HEARTNESS. Independent expert annotation of realistic incidents remains desirable; absent that evidence, retain the existing feasibility-only external-validity statement.

6. **Practicality evidence omits capture/admission/history costs, while the search comparison is too narrow to generalize.** E08 times graph construction/queries after provenance adapters have run; it does not measure capture costs, transactional deep-copy admission or growing event-history persistence. E09 repeats a single small fixture and uses 30 random injection positions, not 30 independent workloads. E11 gives random/Hypothesis 50 ms per trial, while finite checking is characterized separately with a different scope (`n=3`, depth 10 versus search `n=2`, depth 9); there is no direct equal-budget checker comparison. These limitations are mostly honestly stated. **Required action:** add a modest repeated event-workload sweep that measures capture, guarded execution and replay as history/artifact/deployment sizes grow, with traced memory clearly distinguished from RSS. Either add a same-scope, same-budget BFS/random/Hypothesis comparison with startup accounting explicit, or label E11 solely as a comparison of two sequence generators and mark the requested checker-versus-testing experiment unfulfilled. Do not imply that cheap graph queries establish inexpensive enforcement.

## Minor issues

- Main `summary.json` aggregates F1 for origins, while the protocol also requests exact-origin accuracy. Precision/recall/Jaccard/exact values exist in `trace_metrics.csv`; expose the relevant exact-origin and per-family/per-size summaries so a reader need not reconstruct them.
- The stated noise parameter denotes root frequency, not spurious provenance or semantic noise. Retain this distinction in every factor table; missing-edge sensitivity does not evaluate erroneous captured edges.
- E07's 30 runs vary deployment count through only four deterministic values. Reporting repeated protocol validation is correct; report the four unique cases as well as the 30 executions.
- Wilson intervals for 30 missing-event positions have a conditional sampling interpretation on the one fixture; they are not bounds on future implementation defect detection. The same caution applies even when all observations are positive.
- The raw campaign has 1,692 records as reported, and its 18 E05 / 13 E06 record counts match the processed claims in the sample inspection. The preservation of failed historical campaigns and the initial shared abstraction error are strengths worth retaining.
- An archived public package and author confirmation remain necessary for submission; current local paths are useful for this review but are not yet a durable availability statement.

## Questions for the authors

1. What measured result demonstrates a benefit of contracts independent of recorded derivation, given that every generated dependency is also a source?
2. Are the nine family names intended to identify different data distributions, different executable incident workloads, or merely different motivations? Please provide a matrix mapping names to actual changed generation/event behavior.
3. What is the intended affected set when an artifact is inactive locally but remains active only in another deployment? Which raw experiment evaluates that case?
4. What interpretation should be assigned to a property ablation whose challenge never invokes its guarded transition, and why are the separate P4-search and monitor outcomes included as its results?
5. Which missing protocol experiments are considered unresolved deliverables rather than threats that the current paper claims to have addressed?

## Recommendation

**Major revision.** The results are carefully scoped and appear inspectable, but candor about missing evidence is not a substitute for the targeted benchmark, ablation, baseline and runtime experiments above. The practical promise is sufficient to justify revision. Without stronger evidence, the appropriate conclusion remains controlled lifecycle feasibility, as the manuscript already states.
